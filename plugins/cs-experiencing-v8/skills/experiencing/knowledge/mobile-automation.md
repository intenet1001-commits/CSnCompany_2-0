### 108. OCR로 저신뢰도 탐지된 아이콘의 바운딩박스 중심이 실제 탭 타겟과 어긋날 수 있다 (2026-07-14)
<!-- tier: tactical -->
<!-- error-ref: ERR-2026-07-19-001 (addendum) -->

- **상황**: Mega Coffee 장바구니 화면에서 'X' 삭제 아이콘 탭 자동화를 구현하던 중.
- **발견**: Apple Vision OCR이 'x' 아이콘을 conf=0.3의 낮은 신뢰도로만 텍스트로 감지했고, 그 바운딩박스 중심(cx)을 그대로 탭하면 실제로는 옆의 카드 tap-through 영역이 눌려 상품 상세로 이동해버렸다. 실측(cx=920, 976 실패 / cx=1000 성공)으로 실제 탭 타겟이 OCR 바운딩박스 중심에서 +24px 오른쪽에 있음을 확인, 코드에 오프셋 보정을 반영했다.
- **교훈**: OCR 기반 UI 자동화에서 저신뢰도로 감지된 작은 아이콘은 바운딩박스 중심을 그대로 신뢰하지 말고, 인접 tap-through 영역과의 충돌 가능성을 의심해 실기기 반복 실측으로 오프셋을 보정해야 한다. (skeptic verifier DOWNGRADE — 단일 아이콘·2개 측정치에 근거하고 +24px 수치 자체는 이 앱 레이아웃에 종속적이라 principle이 아닌 tactical로 판정. 개념은 "저신뢰도 아이콘은 실측 검증 필요" 수준으로 일반화 가능)
- **근거**: `driver.py`의 `remove_from_cart()` 주석 및 `tap(target["cx"] + 24, target["cy"])` 코드, git 커밋 f4d4014.
- **addendum (2026-07-19)**: 같은 삭제 아이콘 탭 로직에서 +24px 오프셋 보정만으로는 부족한 두 가지 추가 실패 모드를 발견했다. (1) OCR이 실제로 반환한 아이콘 텍스트는 ASCII `'x'`(U+0078)가 아니라 유니코드 곱셈 기호 `'×'`(U+00D7)였다 — `d["text"].strip().lower() == "x"` 비교는 코드포인트가 달라 항상 실패하는 버그였다(`python3 -c "print(hex(ord('×')))"` → `0xd7`). OCR로 기호/아이콘을 텍스트 매칭할 때는 육안 유사 유니코드 변형(x/×, -/—, '/’, O/0 등)을 실제 라이브 출력의 코드포인트 레벨로 확인하고 허용 목록에 포함해야 한다 (skeptic verifier CONFIRM — 기법 자체는 앱/버전 독립적으로 일반화 가능). (2) 동일 정적 스크린샷에서도 일부 카트 행은 아이콘이 육안으로 분명히 보임에도 OCR이 텍스트로 아예 감지하지 못하는 경우가 있었다(재스냅해도 화면이 안 바뀌므로 재시도 무의미) — 이 경우 OCR 텍스트 매칭 자체를 포기하고 고정 x좌표 + 해당 행의 y좌표로 직접 탭하는 좌표 기반 폴백이 필요했다 (skeptic verifier DOWNGRADE — "OCR이 비결정적으로 누락한다"는 주장은 반복 재현 실험 없이 단일 관찰에 근거해 tactical로 판정, 좌표값(998) 자체도 이 앱 레이아웃 종속적).

### 146. 이름 기반 UI 요소 검색은 정확 일치를 전체 스크롤에서 먼저 시도하고, 없을 때만 부분 일치로 폴백해야 한다 (2026-07-19)
<!-- tier: principle -->
<!-- error-ref: ERR-2026-07-19-002 -->

- **상황**: Mega Coffee 메뉴 목록에서 상품명으로 항목을 찾아 탭하는 `open_item()`을 라이브로 테스트하던 중.
- **발견**: 단순 substring 매칭으로 "카페라떼"를 검색했더니, 목록에 더 나중에 나오는 "왕메가카페라떼"(마찬가지로 "카페라떼"를 부분문자열로 포함)가 먼저 매칭되어 실제로는 엉뚱한 상품이 장바구니에 담겼다(결과 확인: 장바구니에 "카페라떼" 대신 "(ICE)왕메가카페라떼" x2가 담김). 정확 일치를 전체 스크롤 범위에서 먼저 시도하고, 그래도 못 찾을 때만 최상단으로 되돌려 부분 일치로 재탐색하도록 고치자 문제가 해결됐다.
- **교훈**: 스크롤 가능한 목록에서 이름으로 UI 요소를 찾는 자동화는 부분 일치를 기본으로 쓰면 더 긴 이름을 가진 다른 요소에 오매칭될 위험이 있다 — 항상 정확 일치 우선, 부분 일치는 폴백으로만 사용한다. (관련: #93은 신원/이름 퍼지매칭에서 같은 문제를 Levenshtein 거리로 해결하는데, 이 경우는 OCR로 읽은 정확한 문자열끼리의 매칭이라 편집거리보다 "정확일치 우선 폴백" 순서 자체가 핵심 처방이다.)
- **근거**: 실측 — `add "카페라떼"` 결과 장바구니 OCR에 "(ICE)왕메가카페라떼" x2로 표시됨; 수정 후 재테스트에서 "카페라떼" 정확 매칭 확인. (skeptic verifier CONFIRM — #93과 정확히 구분되는 컨텍스트의 독립적이고 이식 가능한 검색-순서 버그.)

### 147. dumpsys 등 상태 덤프에서 상태를 판정할 때는 관련 라인만 파싱해야 한다 — 전체 텍스트에 마커 문자열이 있는지로 판단하면 안 된다 (2026-07-19)
<!-- tier: principle -->
<!-- error-ref: ERR-2026-07-19-003 -->

- **상황**: Mammoth Coffee 드라이버의 `ensure_awake()`가 폰 잠금 여부를 `dumpsys window` 출력에서 "Bouncer" 문자열 존재 여부로 판정하던 중, 실제로는 잠금 해제된 상태(스크린샷으로 홈 화면 확인)인데도 "잠김"으로 오판했다.
- **발견**: `dumpsys window | grep -iE 'mCurrentFocus|Bouncer'`처럼 전체 출력에서 마커 문자열을 검색하면, 실제로는 포커스를 잃은 낡은(stale) Bouncer 윈도우 객체가 창 목록에 남아있어도 걸린다. 같은 저장소의 다른 세 드라이버(독립적으로 작성됨)는 이미 `mCurrentFocus` 줄만 파싱하고 있었고 이 버그가 없었다 — 버그가 있는 드라이버 하나만 외부 프로젝트에서 포팅되며 전체-스캔 방식이 딸려온 것으로 확인.
- **교훈**: 상태 덤프(dumpsys 등)에서 특정 상태를 판정할 때는 마커 문자열이 출력 전체에 존재하는지가 아니라, 그 상태를 실제로 보고하는 특정 라인(예: `mCurrentFocus`)만 골라 파싱해야 한다. 유사 코드를 포팅할 때는 같은 저장소 내 동일 목적의 다른 구현과 대조하면 이런 버그를 빠르게 격리할 수 있다.
- **근거**: 스크린샷으로 실제 unlocked 상태 확인 + 동시에 `dumpsys window`에 Bouncer 윈도우 항목 존재 확인; 저장소 내 megacoffee/twosome/starbucks 드라이버는 `grep mCurrentFocus`만 사용해 문제 없음. (skeptic verifier CONFIRM — 3개 독립 구현과의 교차검증 + 스크린샷 반증으로 뒷받침된 파싱-스코프 원칙.)
